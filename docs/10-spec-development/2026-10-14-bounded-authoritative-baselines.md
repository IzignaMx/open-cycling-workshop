2026-10-14. Implemented server-only on integrated main32 `d831cd49136e3d036199a2464b5e422e8608d615`; exact-head PostgreSQL and hosted qualification remain pending. The protocol is deliberately unadvertised (`snapshot_protocol: null`) until that evidence is recorded. This specification includes the reviewed lifecycle and resource-bound amendments.

## R1 and R4: durable start and exact replay

One durable family row is allocated per distinct start. Unique start key is (organization_id,user_id,selected_location_id,authorization_epoch,request_id). request_id is a strict canonical UUID. An immutable StartResponse JSON is retained separately from the latest mutable page response. A start retry checks current bearer/account/scope/epoch and original baseline deadline, then returns exactly the original StartResponse without resetting progress, allocating a family or issuing a different baseline ID. It remains exact after scan, finalize and completion while its baseline deadline remains valid. Replayed context timestamps are historical and never renew a lease.

Future client MUST atomically store request_id, exact start body, identity, epoch and generation before HTTP; no bearer token is stored. Reload after fresh online verification resumes the validated durable phase/expected continuation. Same-epoch token renewal does not change the attempt. A replayed StartResponse must never overwrite progressed local continuation. Missing/contradictory progress holds; changed context supersedes the attempt without reassigning it. Distinct baseline IDs require distinct empty partitions. These are requirements and future browser tests, not implementation in this server slice.

Two in-progress baselines per authenticated global user ID + selected location, counting across epochs. No installation_id or new device credential. Neither start may take over or cancel the other. Full slots produce 409 baseline_in_progress with retry_after_seconds and expires_at for the earliest releasing slot, never another attempt's IDs/tokens/data. Retry does not slide the occupied slot's expiry. Clients use capped exponential backoff with jitter, stop while offline, and respect Retry-After.

## R2: one bounded checkpoint family, absolute clocks and quotas

A family has immutable created_at, baseline_expires_at=min(created_at+30m, originating validated JWT exp), and family_expires_at=min(created_at+8h, originating validated JWT exp). The checkpoint family deadline is chosen at start, never at each completion; login renewal, activation validation and empty incremental polling never extend it. Before initial completion, retention ends at baseline_expires_at. At initial completion the row becomes a completed family retained until family_expires_at; this only changes which predeclared deadline controls cleanup. A baseline that fails to complete before its deadline cannot become a checkpoint.

There is ONE mutable bounded-run state and ONE monotonically increasing token sequence per family. Each scan/finalize/delta transaction replaces a single latest predecessor hash + exact JSON response (maximum 1 MiB). Only the immediately preceding request replays; older progression tokens return continuation_stale. Replaying the completion request returns the identical completed checkpoint, including an empty completion. Starting an incremental run from a checkpoint captures a finite H and advances the same row; completing it does not allocate rows. Checkpoints do not branch.

Store the current completed checkpoint token hash and its baseline identity independently from latest response cache. validate-activation is repeatable, read-only and non-advancing; it accepts only the initial baseline completion checkpoint while the family has not begun incremental progression. Starting incremental progression invalidates activation of the original checkpoint explicitly (continuation_stale); later completion checkpoints are incremental, not new baseline activation proofs. Activation remains valid past baseline_expires_at until immutable family_expires_at, since its proof is in the retained family row. Revalidation returns fresh authenticated context but does not extend any pagination deadline.

Hard caps under the organization barrier: 2 active baselines per user/location across epochs; 8 total live families per global user across all locations/epochs; 100 active baselines per organization; 128 total live families per organization. Current users.id is globally unique and belongs to one organization, so org→actor locking also serializes the global-user quota; moving an identity between organizations is unsupported. No unexpired family is evicted. General capacity produces 429 baseline_capacity with safe earliest releasing expiry and Retry-After. Each family stores <=16 KiB immutable start JSON, <=1 MiB last response JSON and <=16 KiB auxiliary bounded JSON; strict DTO/cardinality limits and database byte CHECKs enforce this. Total persisted JSON is therefore <=8.25 MiB/user and <=132 MiB/org, excluding fixed row/index overhead. No bearer tokens, password material or secret keys are stored.

Cleanup is metadata-only, organization-scoped and bounded to 128 expired family rows selected in deterministic primary-key order. It runs under the existing org barrier before admission; physical rows remain bounded because allocation follows cleanup and the physical count cap. Cleanup never acquires another organization's or actor's lock after pagination locks. If corrupt/unexpected excess historical rows exist, admission fails safely rather than bypassing the bound. Metadata cleanup is not business/journal/history deletion.

## DTOs and transport

Closed snake_case schemas, protocol literal 1, required nullable keys, RFC3339 UTC output. IDs preserve spelling, 1..36 characters; entity_version and payload.version are strict positive safe integers (no bool/fractional coercion). Read strings accept the stored domain values, including supported sync-written Text values longer than REST create limits. No truncation or skipping. Every envelope ID/version/type and payload scope agrees with the authenticated family. Unknown projection keys/states fail closed.

Shared record: {entity_type,entity_id,entity_version,payload}, discriminated customer/bicycle/service_order payloads with exactly the keys in sync/projections.py. Customer nullable email/phone; bicycle nullable model/bicycle_type/wheel_size/notes; order nullable bicycle_id/intake_condition/accessories/diagnosis. The nine existing order states remain the exact enum; priority remains string. Canonical output normalizes timestamp offsets/UTC spelling before equality.

POST /api/v1/sync/baselines/start: request {protocol,selected_location_id,authorization_epoch,request_id}; response {protocol,baseline_id,context,continuation,expires_at} where expires_at is the baseline deadline.
POST /api/v1/sync/baselines/page: request {protocol,continuation}; response {protocol,baseline_id,authorization_epoch,page_id,predecessor,records,phase:scan|scan_complete,continuation}.
POST /api/v1/sync/baselines/finalize: same request; response {protocol,baseline_id,authorization_epoch,predecessor,continuation}.
POST /api/v1/sync/deltas/page: same request; response {protocol,baseline_id:string|null,authorization_epoch,page_id,predecessor,records,phase:catching_up|complete,continuation,completion:null|{baseline_id:string|null,authorization_epoch,checkpoint}}. Initial baseline deltas carry baseline_id; incremental runs carry null. Completion.checkpoint equals continuation.
POST /api/v1/sync/baselines/validate-activation: request {protocol,checkpoint}; response {protocol,baseline_id,authorization_epoch,checkpoint,context}.

Control request bodies <=16 KiB, including chunked requests (enforce before parsing); continuation/checkpoint <=512 ASCII bytes; fixed 100 records and <=1 MiB entire serialized response, including envelope/token/completion overhead. One too-large row gives 413 projection_too_large with no advancement; byte truncation stops before that row and never returns a false empty progress page. All success/error/redirect responses on these paths are no-store. Continuations appear only in POST bodies, not URLs.

Explicit errors retain ApiError envelope: invalid_session, capability_denied, scope_denied, context_changed, snapshot_required, continuation_stale, dataset_changed, baseline_expired, checkpoint_expired, cursor_invalid, unsupported_protocol, projection_too_large, baseline_in_progress, baseline_capacity, temporary_unavailable. Existing context/auth HTTPException and Pydantic safe error shapes are preserved and documented, not falsely described as ApiError-only.

## Opaque codec and durable metadata

Token b1.<192-bit random reference base64url>.<canonical unsigned sequence>.<purpose>.<HMAC-SHA256>; purpose scan/finalize/delta/checkpoint. Sequence 0..2^53-1, fail closed on exhaustion. Strict ASCII/canonical grammar prevents alternate encodings. MAC uses a fixed non-JWT domain separator plus exact prefix, with existing injected Settings.auth_secret supplied at app composition. No key creation, credential reading or new persistent access. Compare signature constant-time before DB reference lookup. Store SHA256(reference) as key; response JSON necessarily retains issued continuation metadata, which is not authority. Ordinary bearer auth is mandatory for every lookup/replay.

Single additive table: hashed reference PK; baseline UUID; principal/org/location/epoch/policy binding; request_id; created/baseline/family/retention deadlines; scan maxima/positions bounded to three types; phase; W/H/covered cursor; sequence; immutable start JSON; latest predecessor hash/response JSON; initial activation checkpoint hash and eligibility. Index start key, org/user/location/phase, org/retention deadline. Composite tenancy FKs where supported. New business-table scan indexes use (organization_id,location_id,id COLLATE C). Migration downgrade is allowed only for an empty pagination table. PostgreSQL takes an ACCESS EXCLUSIVE table lock before checking emptiness and holds it through the migration transaction; retained proofs cause refusal without schema or data removal. Successful downgrade removes only the empty family table and this increment’s indexes. Use a schema-compatible application rollback when proofs remain; maintenance must exclude mixed application versions.

## R3: bounded queries and transaction authority

Every operation: validate original signed session → set PostgreSQL LOCAL lock_timeout=2s and statement_timeout=5s → lock organization → reload/lock actor populate_existing → literal effective_principal(original,current account) → normalize surviving concrete grants → validate selected location and epoch → lock family (if applicable). No session-first lookup for organization discovery. Continuation requests carry no selected location or epoch: after original principal organization/actor locks, load the family by hashed reference AND authenticated organization/user, then derive its selected location and epoch and validate both against current effective authority under the same locks. Foreign and nonexistent family references have the same failure. Explicit session.commit() persists every successful start/progression/replay path before returning; the existing get_session dependency does not commit success. Required sync.pull plus per-type customers.read/bicycles.read/orders.read. Role, owner, write grants and token possession grant no implicit read. Signature/scope/binding failure never reveals another family's existence. Recheck JWT expiry after locks and immediately before explicit commit, including cached replay; rollback on any failure.

Scan bounds/comparison/order/index share C collation on PostgreSQL (binary equivalent SQLite tests are not PostgreSQL proof). Capture scoped max ID with ordered LIMIT 1; page each authorized type with scoped keyset and LIMIT 101. Capture organization watermark via indexed cursor DESC LIMIT 1. Add (organization_id,location_id,entity_type,cursor) feed index. For every delta page fetch at most 101 records PER authorized type (at most 303 candidates), merge by source cursor, then apply record/byte cap. Each branch has all equality scope predicates before cursor bounds. No unfiltered hidden-row walk and no unbounded IN query relying on outer LIMIT. Candidate selection first obtains bounded IDs/cursors and database-side decompressed serialized byte lengths (for feed JSON, octet_length(payload::text), never compressed pg_column_size), not arbitrarily large Text/JSON values. Select only a response-budget-bounded prefix and load a candidate projection only after its conservative measured size fits the budget; final full-wire serialization remains the exact size authority; reject a single over-budget row explicitly. This avoids materializing up to 303 unbounded historical payloads before applying the response cap. PostgreSQL size/plan tests must cover a very large stored Text and JSON value. Zero read types yields explicit empty completion without accessing hidden projections. Timeouts rollback and return 503 temporary_unavailable with Retry-After, never completion.

## Historical projections and W/H proof

All supported writers must hold the PR31 organization barrier through domain/feed/outbox commit. Start captures W plus fixed authorized table maxima. Scan returns full current persisted rows, including historical direct-REST rows with NO feed entry. It does not reconstruct historical current state from old/incomplete feed payloads. Finalize only after every scan bound is exhausted captures immutable H under the same barrier. Catch-up reads full PR31 projection records in (W,H], not current-table joins that could inject post-H values. Rows before W need no feed backfill. Deploy without mixed old writers; any malformed projection in the requested range fails explicitly.

For each row present at H: if present at W, its immutable ID is within captured max and scan visits it; any later update through H is in the feed. If created after W, create/update feed covers it even below an already scanned ID, above max or in an initially empty table. Scan values can be newer than early feed values, so client version dominance is mandatory. Scan occurs before H and deltas are <=H, so maximum observed version is exactly H state. Hidden-only ranges and cursor holes complete at H without exposing numeric watermarks/counts. Post-H writes belong to the next finite run. Delete, scope move, pruning and restore violate the proof and remain unsupported activation boundaries. Server issuance does not prove browser durable consumption or acknowledge any queued mutation.

## R5: future client fencing obligation

Any post-commit volatile ticket assignment MUST compare generation, tabAttemptId, activePartitionId and exact expected ticket; stale assignments cannot replace a newer same-generation partition. Separate rollback-to-HELD control transactions compare all those fences before changing state. Tests must force older beginBaseline completion last, user switch before HELD, quota abort and delayed activation against new baseline; winner remains usable and journal is byte-identical. Server returns bound baseline/epoch/predecessor metadata but does not claim to implement browser fences.

## Implementation and evidence record

- New modular server files isolate wire validation, opaque metadata codec, SQL readers, metadata admission, progression and HTTP transport. The context handler shares its existing literal-authority helper; its outputs and advertisement remain unchanged.
- PostgreSQL query preflight measures JSON-serialized field bytes plus a conservative 2048-byte envelope allowance before loading a body. Page assembly sizes its actual serialized response envelope, then checks exact UTF-8 serialization. Materialization separately allows at most 1 MiB plus 2048 bytes for current-row estimates, and six times 1 MiB plus 2048 bytes for historical JSON estimates to account for ASCII escape expansion. Only one candidate is loaded at a time. A last near-limit record may be followed by an empty completion page when the completion envelope cannot fit beside it; values are never truncated/skipped and no unbounded body is loaded. Ordinary supported sync Text exceeding REST request limits remains valid below the bounded read budget.
- First red: lifecycle endpoint tests returned 404 before routes existed; wire/query module tests failed imports before implementation. Initial green covered historic no-feed rows, replay, capacity, authenticated context regressions and strict DTOs. Expanded lifecycle includes 1,000 empty incremental polls with one row and an unchanged absolute deadline.
- Local PostgreSQL tests explicitly skip without a configured dedicated safe test database. Authored adversarial lock/expiry/race/timeout and EXPLAIN/BUFFERS cases are not a PostgreSQL pass claim. Exact final counts and review disposition are recorded at publication qualification.
- Existing production v4, inactive kernel, phase-separated CI artifacts and retry-free PWA cases are unchanged. No installation, credential change, deployment, old-writer cutover or browser activation was performed.
