# V0.2 Workshop Core · Bicycles + Service Orders Implementation Plan

> **For agentic workers:** implement task-by-task with the Master Agent Loop v0.2 (test first, evidence before status). Steps use checkbox (`- [ ]`) syntax. V0.1 physical gates (R01-T035) run in parallel as manual work; V0.2 implementation must not weaken any V0.1 gate.

**Goal:** Extend the verified Customer vertical slice with the Workshop Core: bicycles as a first-class synchronizable entity and service orders with a validated state machine, tasks, and offline-first intake — all through the existing sync engine (durable queue, idempotent push, cursor pull, conflict center).

**Scope (FR coverage in this increment):**

- `FR-BIK-001` create bicycle without an active order; `FR-BIK-003` technical data basics (brand, model, type, wheel size, notes); `FR-BIK-006` service history surfaced through the order link.
- `FR-SVC-001` order from existing customer + existing/new bicycle; `FR-SVC-002` reported problem separated from technical diagnosis; `FR-SVC-003` intake condition + accessories; `FR-SVC-004` priority, owner, date, location; `FR-SVC-005` validated state machine; `FR-SVC-010` simple task list per order; `FR-SVC-016` auditable timeline (append-only events per order).
- Explicitly out of scope here: budgets (FR-SVC-007/008/009), inventory reservation (FR-SVC-011), QC config (FR-SVC-013), rework (FR-SVC-014), receipts (FR-SVC-018), photos (FR-BIK-004), QR (FR-BIK-007).

**Architecture:** identical to V0.1 — Python modular monolith (FastAPI/Pydantic/SQLAlchemy 2/Alembic) with mutation log + change feed + capability RBAC; React 19 + Vite PWA with Dexie local repositories and the existing `SyncCoordinator`. Two new synchronizable entity types (`bicycle`, `service_order`) ride the SAME push/pull pipeline: the envelope widens its `entity_type` union, and pull-merge fans out per entity.

**Key domain decisions to enforce:**

- Service-order state machine (server-authoritative transitions, mirrored locally): `INTAKE → DIAGNOSIS → AUTHORIZED | REJECTED → IN_PROGRESS → (WAITING_FOR_PARTS ⇄ IN_PROGRESS) → READY → CLOSED`, plus `CANCELLED` from any pre-READY state. Invalid transitions are permanent (conflict), not retriable.
- Order updates carry `base_version` exactly like customers; a stale transition becomes a `sync_conflict` with `error_code=invalid_state_transition` and lands in the Conflict Center.
- Timeline events are append-only (`service_order_events`), created in the same transaction as the transition; they never update, only insert.
- Bicycles belong to a customer within the organization scope; deleting a customer with bicycles or open orders is rejected (compensating flows are out of scope).

## Global Constraints
