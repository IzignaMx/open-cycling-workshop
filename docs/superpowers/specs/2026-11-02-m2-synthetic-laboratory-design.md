## 1. Purpose and admission

Prove one useful boundary: a separate process reads a bounded product catalogue from a server that authenticates a dedicated machine identity, checks current scoped grants and can revoke it. This is an independent prerequisite under Master Loop §5, not V0.1 acceptance or opening V0.2. Physical T1–T8/R01-T035, full recovery/capacity gates, SPENT40927223929 and historical UNKNOWN remain unchanged. M1 is accepted via PR82/fresh-main receipt; older source checkpoint wording is historical, not a new blocker.

M2 strategy expressly requires identity, expiry/rotation/revoke audit, one resource, own store, no default enablement/real data, and adversarial isolation evidence. Traceability: partial FR-PLG-003/004/005/007/008/009 and SEC-002/003/005/006/007/010; prerequisite only for R09-T020/R10-T014. No SDK, registry, events, commands, payments, offline replay, generic loader, runtime plugin installation or production integration.

## 2. Approaches and recommendation

**A. Closed laboratory boundary (recommended):** implement later only in a dedicated test application composition and separately launched fixture connector. Use actual PostgreSQL 18 authorization transactions and a real HTTP read. Production app does not import/mount the connector router or provisioning code; no environment flag can activate it. A disposable synthetic database and network are created by an explicit harness, never an operator-supplied existing database URL. This demonstrates real auth/isolation without opening production access. Cost: promotion later needs an additional reviewed production provisioning/migration/security package; laboratory results are not production qualification.

**B. Production-ready but default-disabled connector subsystem:** add machine tables, operator management API and activation controls to normal application now. This would force grant bootstrap, durable secret provisioning, upgrade/restore and operational retention decisions now. Not recommended and not authorized: default-off alone is not adequate separation from real data.

For A credentials, prefer **opaque database-backed random bearer credentials** over dedicated signed machine JWTs. Both still require current database grant/revocation checks, so signed tokens add key/audience/algorithm/rotation complexity without removing the transaction. Do not reuse human JWT signing keys or human session identities. A bearer credential can be replayed while valid by someone who steals it; this design limits its authority/lifetime, not claims proof-of-possession or replay prevention for every read.

## 3. Closed synthetic execution boundary

All details here are **proposed lab policy**, not production defaults:

- Dedicated test composition absent from normal app imports/OpenAPI/startup. A production endpoint absence test is mandatory, including with misleading enable flags and machine credentials.
- Harness creates a new isolated PostgreSQL database from reviewed fixtures, two organizations/two locations and deterministic synthetic product values. It refuses existing database names, imported backups and general DSNs; never loads environment production credentials or customer exports. Product names/SKUs are potentially confidential, so field choice alone does not prove synthetic data.
- A separate, non-root connector process has a read-only root filesystem, no Docker socket, no host/core mounts or Core DB credential, and only its own bounded temporary store. The orchestrator may create the containers; the connector itself never receives orchestration authority.
- Private test network permits connector egress only to the named lab API TLS endpoint; no Internet/provider callbacks/redirect following. No host port publishing. Test CA is run-local, connector verifies certificate and hostname; no disabled TLS verification. CA/credential material remains ephemeral and excluded from logs/artifacts. Network-denial evidence must be enforced, not an allowlist assertion in Python.
- Proposed connector budget: one in-flight request, maximum four pages/run, 128 MiB memory, 0.5 CPU, 32 PIDs and 16 MiB temporary volume. Server uses a dedicated maximum-two-connection read pool; canonical transaction/lock/statement budgets 8/2/5 seconds remain. Enforce server-side maximum two concurrent requests with no application wait queue, an OS/listener backlog capped at8, maximum120 requests and20 failed-auth attempts per run (global lab counters, not caller-controlled identity/IP); reaching a budget closes further admission. Bounds are checked before database work. Header aggregate8 KiB, credential128 bytes, raw query1 KiB, no GET request body, and64 KiB response maximum are enforced at the earliest supported transport/application boundary; parser-incomplete input and slow clients also have transport byte/time limits. If the selected server cannot enforce these, stop for design correction rather than calling cooperative client limits protection. Exact overload response can be429 or transport503, never unbounded queuing. If an executor cannot enforce a limit, that check is blocked, never green by simulation.
- Harness enforces a non-extendable15-minute run wall deadline, terminates and reaps API/connector processes and removes resources on timeout; hard kill after a bounded5-second graceful interval. No automatic retry or refresh. Offline/401/403/timeout terminates the example with a bounded, secret-free status. No queued writes or delivery. Core startup/login/capture do not depend on this process.

## 4. Identity, credentials and operator boundary

The test harness is the only lab lifecycle operator, invoking an internal fixture administration interface unavailable over HTTP. This is **not** a production admin bypass or grant bootstrap pattern. No human account receives any new capability; historical wildcard/catalog and starter roles stay unchanged. Production operator identity, explicit management capability and bootstrap/recovery are deferred, not inherited from Owner.

Proposed fixture data model, separate from human users/audit and not a production Alembic migration:

- Installation: opaque lab installation ID, org ID, active flag, explicit allowed location and allowed capability. Installation identity is distinct from organization, dataset incarnation and run identity; the current platform has no installation identity model to reuse.
- Machine: ID, installation/org/exact location, enabled flag, explicit `catalogue.read` test capability, generation, issue/expiry times and credential verifier. Only one location and one resource in this slice; no wildcard/unscoped identity.
- Credential: 256 random bits, format-tagged opaque secret; server stores only SHA-256 verifier plus non-secret identifier/metadata. Bound input length and constant-time verifier comparison; no plaintext in database/audit, URLs, argv, environment, reports or exception strings. Transfer once through a run-local restricted read-only credential file on temporary storage; revoke on failed delivery, do not redisplay.
- Proposed absolute lifetime **15 minutes**, no sliding renewal or refresh token. Rotation atomically revokes old credential/generation and installs the replacement, **zero overlap**. Losing the replacement requires another explicit lab rotation, not retrieval. This availability tradeoff is intentional for a short diagnostic, not a future production lifetime decision. Expiry is the earliest of UTC expiry, a non-resettable per-credential elapsed deadline and the original run deadline; rotation cannot extend that run deadline. Proposed lab execution is Linux with a suspend-inclusive monotonic clock (CLOCK_BOOTTIME) required; unavailable/non-finite/backward monotonic evidence fails closed. Compare UTC samples against the prior high-water mark and fail closed on backwards UTC movement; check deadlines before and after materialization. Restart never reconstructs elapsed deadlines from a database or connector input: it invalidates the run. Clock drift/jumps may refuse service conservatively; no production trusted-time claim.
- Current installed scope ∩ machine scope ∩ credential-generation scope ∩ endpoint policy must permit the request. Human JWTs, machine credentials at human routes, unknown credential types and missing/ambiguous authorization headers are refused. No cookies/CORS/browser bearer distribution.
- Secret-free append-only lab audit records lifecycle events (issue, enable/disable, grant change, rotate, revoke), org/installation/machine/non-secret credential ID, actor category `fixture_harness`, time, request ID and changed non-secret policy fields. Atomic lifecycle transaction includes its audit event; audit failure rolls back the change. Audit rows live only in the disposable lab database for that run, then are removed with it; outside the run retain only bounded secret-free qualification counts/statuses, not audit-row exports. Existing human audit target enums/FKs are not silently relaxed.

## 5. Restart, restore and revocation semantics

Each lab API start receives a new random **run instance ID held outside the database** by the trusted harness, never accepted from a restored database, environment supplied by the connector or HTTP input; installation/machine/credential records bind to it and the current dataset incarnation. Machine reads require exact valid incarnation even if human legacy protocol compatibility accepts a missing claim. No inference that organization ID is installation authority.

Restart is fail-closed: old run credentials cannot be used; harness creates a new synthetic installation. Fixture database snapshots are never accepted as fresh installations. A restored old database under a new run fails the run binding. Harness refuses in-place restore while API is running and stops it first. A privileged administrator arbitrarily rolling back a live database and its external run witness is outside the laboratory guarantee; production anti-resurrection needs a separately designed durable restore fence. No claim of full crash/recovery safety.

Read authorization uses a dedicated machine principal, not `Principal.user_id` populated with a fake user. A bounded verifier lookup may locate candidate IDs but confers no authority. Then one database transaction acquires locks in canonical order: organization compatibility → installation → machine/credential generation. Re-read verifier/state under those locks; check run binding, current incarnation, active flags, absolute expiry and scope intersection. Every lifecycle mutation uses the same lock order/barrier; grants reside in those protected records for this slice. Installation/org/location/incarnation identity is immutable within a generation; changing it revokes the generation and requires explicit fixture reissuance. Grant reduction, disable, rotation and revoke all use this barrier; grant expansion is never automatic and requires explicit fixture administration with a new credential generation. Query only the derived tenant/location, fully materialize the closed DTO, recheck expiry/time budget, then rollback/cleanup before releasing any response bytes. SQL failure/unsupported timeout control/cleanup failure yields no partial body and invalidates unusable connections.

**Linearization contract:** a revoke/grant reduction that commits before a read obtains the barrier makes that read fail. A read that already owns the barrier can finish before revoke commits, within the bounded transaction; revocation does not retroactively cancel that authorized read or recall bytes. After revoke acknowledgement, no later authorized read/retry may begin with the old credential. OS/network buffered delivery of an already-authorized response may occur later; do not promise zero bytes delivered after wall-clock acknowledgement. No streaming. Crash releases database locks; no connector failure changes Core business data.

## 6. Proposed single public contract (lab composition only)

`GET /api/v1/connector-catalogue/products`

Authorization: dedicated opaque machine bearer format. Closed query: `limit` default25, range1–50; `offset` default0, range0–200; reject duplicates/unknown keys/oversized raw query. Identity determines org/location; no tenant/location selectors from body/query/manifest. Stable product-ID order; normal read-committed page semantics, **not a cross-page snapshot**. Maximum serialized body64 KiB; exceed → bounded failure, never truncate an item silently.

Response: `items` containing only `product_id`, `sku`, `name`, `unit`, `version`; `next_offset` or null within the bounded window. Version is the product version, not an SDK/global consistency promise. No stock count, prices, contact data, actors/orders/notes, movement history, total counts or full model exports. Machine lacks all other endpoints and all write authority. A hypothetical confidential SKU/name remains prohibited in this lab by fixture enforcement.

Invalid credentials: generic401; valid credential without current permission: generic403; malformed permitted query:422 after auth; unsupported/budget/storage conditions: generic503; resource budget/rate refusal:429 where applicable. No identity enumeration or raw SQL errors. All private responses and errors use `Cache-Control: private, no-store`; no ETag, service-worker cache, telemetry or response-body logging. This is an API contract proposal, not a registered route.

## 7. Own store and disposal

Connector owns only a small SQLite projection in its 16 MiB temporary volume, partitioned by run/installation/org/location/incarnation; replace a received page transactionally. No credential is stored there and no authoritative inventory state is inferred. It is not an offline cache: only the current successful fetch can be shown as current; failure stops rather than serving stale values. No export endpoint in this slice.

Store exists only for the explicit run (maximum15 minutes), purged on normal exit and removed by harness cleanup after crash. Cleanup receipt covers credential files, CA private keys, database including lifecycle audit, SQLite/temporary volumes, network and process termination separately. Any leftover resource is reported by non-secret identifier; no raw credential or database dump is retained. Cleanup failure is recorded as failure; do not claim erased files if removal fails. Even temporary storage is not cryptographic secure erasure and may be paged/backed up by the host. No production retention or uninstall/purge policy is implied. Production durable retention/export requires separate consent.
